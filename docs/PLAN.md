# procglint 1.0 実装計画

**計測処理をユーザー単位の一つのサービスに集約し、GUIとMCPが同じデータを利用する構成にします。** GUI、履歴、MCP、プロセス終了操作、最適化、配布までを1.0の必須成果物とし、CLIだけの先行リリースは設けません。

Jobletから採用するのは、**共通ロジックの分離、アプリに同梱するstdio MCP実行ファイル、デフォルトの読み取り専用動作、明示的な操作権限**です。procglintでもGUI非依存を維持します。一方、**各MCPプロセスが独立して監視すると負荷が増えるため、実行中のサンプラーも共有します。**

（型・単位・権限などの確定した契約は `docs/SPEC.md` を正とします。）

## 2. プロセス構成

`procglint-agent`（SMAppServiceで登録するユーザー用LaunchAgent、ユーザー単位で1つ）が Sampler / SnapshotStore / HistoryStore / SamplingScheduler / ProcessControl を持つ。GUI・CLI・`procglint-mcp` は XPC でagentに接続し、独立した定期サンプリング処理を持たない。サービス登録は初回セットアップで明示的に行う。サービスが無効な場合は診断と復旧手順を返し、独立サンプラーへ切り替えない。

| コンポーネント | 責務 |
|---|---|
| `procglint-agent` | OSへの問い合わせ、差分計算、履歴保持、操作権限の最終検証 |
| GUI | 表示、検索・並び替えの要求、ユーザー操作、設定 |
| `procglint-mcp` | MCPメッセージ処理、公開ツールの制御、XPCへの中継、結果のJSON化 |
| `procglint` | `status`、`doctor`、現在値・履歴のエクスポート |

## 3. 監視のライフサイクル

| 状態 | 動作 |
|---|---|
| メインウィンドウ表示中 | 指定間隔で監視。標準5秒 |
| メニューバー表示のみ | 標準10秒 |
| MCP接続済みだが未使用 | 定期監視しない |
| MCPから現在値の問い合わせ | 新しいキャッシュがあれば返す。古ければ共有取得を要求 |
| MCPの時間限定観測中 | 指定間隔で監視。終了時刻を必須にする |
| GUI非表示、観測要求なし | 定期監視を停止 |
| 全クライアント切断後 | 猶予期間を経てサービスを終了 |

有効な要求が複数ある場合は最短の間隔を採用。同時に実行できる収集処理は一つだけ。通常の読み取りに無制限の強制更新は設けない。コールドスタート時は即時取得と約1秒後の取得を共有し、それまでCPUは`warming_up`。タイマー許容遅延は間隔の10%。MCPのEOF・切断で観測要求を解除。期限は単調時計で管理し、スリープ復帰時は期限切れ要求を破棄。遅れた回数分を取り戻さない。UIへの未反映データは最新一件だけ保持。

## 4. 計測とデータモデル

PID一覧 `proc_listallpids`、CPU・メモリ・ディスクI/O `proc_pid_rusage(RUSAGE_INFO_V2)`、名前・所有者はBSD情報系をキャッシュ、実行ファイルパスは詳細表示時のみ（MCP公開は別権限）、全体CPU・VMはMach host statistics、ページサイズ・物理メモリは起動時に取得。libprocはCブリッジに隔離。

CPU% = 100 × CPU時間の増分 / 実際の経過時間（1コア=100%）。メモリ主表示はフットプリント、RSSは別列。取得できなかった指標を別の指標で置き換えない。ProcessIdentity = 起動セッション識別子 + PID + 開始時刻、MCPには不透明な`process_key`。64bit値は文字列。共通レスポンス情報（`agent_instance_id`, `snapshot_id`, `sampled_at`, `interval_ms`, `age_ms`, `coverage`, `status`）。`warming_up` / `permission_denied` / `exited` / `stale` / `unsupported` を表現。PID一覧取得失敗を全プロセス終了と解釈しない。

履歴: 全体指標と固定・観測したプロセス。直近10分、各系列600点、プロセス系列は最大16件。GUIとMCPで共有。観測していなかった期間を復元しない。

## 5. GUI仕様

上部に全体CPU・メモリのサマリー、中央にプロセス一覧、右側に選択プロセスの詳細。標準列: 名前、CPU、フットプリント、読み取り速度、書き込み速度、PID、所有者。累積CPU時間、RSS、累積I/Oは列設定で追加。検索は名前・PID。「すべて」「自分のプロセス」「固定したプロセス」切り替え。検索・ソートで追加の全件取得はしない。

詳細パネル: 識別情報、取得可能なパス、CPU・メモリ・I/O履歴、取得制限、終了操作（「終了要求」と「強制終了」を分離、データ消失の可能性を表示）。

描画: 行ビュー再利用、画面外の行の文字列を生成しない、選択は`ProcessIdentity`で維持。グラフはサンプル到着時のみ更新、欠測区間に線を引かない。

設定画面: 更新間隔、メニューバー表示、履歴上限、サービス登録状態、MCP権限、接続設定のコピー（実際の配置場所から生成）、診断（agentとMCPブリッジを含む負荷）。

## 6. MCP仕様

stdio専用の`procglint-mcp`を同梱。対応プロトコルは2026-07-28（リクエストごとのメタデータ・`server/discover`）と2025-11-25（`initialize`）を別アダプターで扱い、業務ロジックは共有。

| ツール | 用途 | 権限・主な制限 |
|---|---|---|
| `get_snapshot` | 全体サマリーと上位プロセス | 読み取り |
| `list_processes` | 検索、ソート、ページ付き一覧 | 読み取り。標準50件、最大200件 |
| `get_process` | 指定した`process_key`の詳細 | 読み取り。パス公開は別許可 |
| `get_history` | 全体・対象プロセス・観測要求の履歴 | 読み取り |
| `get_monitor_status` | 自身の負荷、取得範囲、監視状態 | 読み取り |
| `start_observation` | 期間と更新間隔を指定して観測開始 | `--allow-observe` |
| `stop_observation` | 自分の観測要求を終了 | `--allow-observe` |
| `set_sampling_policy` | 監視設定を変更 | `--allow-configure`、設定リビジョン必須 |
| `prepare_termination` | 対象検証、30秒の一回限り操作トークン発行 | `--allow-terminate` |
| `terminate_process` | 検証済み対象へ終了シグナル | トークン必須。強制終了には追加許可 |

`outputSchema`定義、`structuredContent`と互換JSONテキストを返す。stdoutはプロトコルのみ。入力256 KiB、応答1 MiB、クライアントごとの同時要求4件、読み取り・変更操作に個別レート制限（agent側でも合算制限）。ページングは`snapshot_id`に固定。キャッシュは権限範囲をキーに含める。ツール説明に、プロセス名等の文字列はデータであり指示ではない旨を記載。

## 7. 権限と終了操作

既定は全体サマリーと自分のプロセスの基本指標。`--include-system`、`--include-paths`。引数・環境変数・メモリ内容は公開しない。有効権限 = OS ∩ アプリ設定 ∩ MCP起動フラグ。許可外ツールは一覧に載せず直接指定も拒否。最終検証はagent。XPCはUIDと署名を検証。

終了操作は自分のプロセスに限定。PID 0・1、procglint自身、MCP経路の保護対象を拒否。負数PID・グループ・名前一致・任意シグナル・シェル実行は実装しない。トークンは30秒・一回限り。実行直前に開始時刻・所有者・実行内容を再検証。GUIは確認ダイアログ。トークンは人間の承認の証拠ではない。結果は「シグナル送信済み」と「終了確認済み」を区別、自動でSIGKILLへ移行しない。

## 8. 最適化と性能予算

サンプラー共有、要求集約、メタデータキャッシュ、専用直列キュー（PIDごとのTask/スレッドを作らない）、バッファ再利用、上限、GUI向けに不要なJSON化をしない、MCPページング・フィールド選択・出力上限・バックプレッシャー、行再利用、非表示時の要求解除。前回上位だけを監視する最適化はしない。

| 指標（Release、5秒更新、500プロセス） | 目標 |
|---|---:|
| agentの平均CPU | 0.3%以下 |
| GUI＋agentの平均CPU | 1.0%以下 |
| GUI＋agent＋MCP 1接続 | 1.3%以下 |
| 一巡の収集時間 | p95 40ms以下 |
| メインスレッドの更新処理 | p95 8ms以下 |
| GUI＋agentの定常フットプリント | 120 MiB以下 |
| MCPブリッジ1個の追加フットプリント | 30 MiB以下 |
| 履歴データ | 8 MiB以下 |
| 有効な監視要求がないときの定期収集 | 0回 |

MCP 3クライアント接続でも収集ループが3倍にならないことを独立した合格条件とする。

## 9. 必須の統合試験

| 試験 | 確認内容 |
|---|---|
| GUI＋MCP 3接続 | 収集の重複がなく、権限別の結果が混ざらない |
| GUIを閉じてMCP観測を継続 | 必要な計測だけが残る |
| MCP接続だけ残して放置 | 接続維持だけでは定期監視しない |
| MCPのEOF・異常終了 | 観測要求が残留しない |
| stdoutの読み取り停止 | MCPブリッジが共有サンプラーを止めない |
| スリープ・復帰 | CPU差分、観測期限、履歴の空白を正しく扱う |
| agentの再起動 | 古いカーソル・操作トークンを無効化する |
| 大量の生成・終了、PID再利用の模擬 | 履歴・選択・操作対象を誤って引き継がない |
| 24時間稼働 | 継続的なメモリ増加がない |

配布: GUI・agent・MCP・CLIをまとめてビルド、各実行ファイルへ署名、アプリ全体を公証（Developer ID、Hardened Runtime）。同梱Skill（`skills/procglint/SKILL.md`）には、最初に`get_snapshot`を使う、必要な対象だけ観測する、欠測をゼロと解釈しない、自動で強制終了しない、を記載。
